모니터링 (대시보드·로그 이력)

AI 엔진 운영 현황을 보는 탭 셸 화면입니다. 중첩 라우트로 5개 탭 전부 실제 화면(현황 대시보드 / 솔루션별 작업현황 / 솔루션별 연동현황 / GPU 사용현황 / 로그 히스토리)을 딥링크 가능하게 배선합니다. 현황 대시보드(MN-001)는 요약카드 6종과 위젯 5종을 self-contained 방식으로 조립하고, 작업현황·연동현황 두 탭은 축(axis)만 다른 공용 통계 셸을 재사용하며, GPU 사용현황 탭은 서버별 리소스 카드·트렌드·저장 이력을 갖춘 독립 구현입니다.

기능 개요

모니터링은 VAMS가 돌리는 AI 엔진들의 하루 운영 상태를 한눈에 보는 메뉴입니다. 껍데기는 탭 셸(MonitoringPage)이고 탭 5종(현황 대시보드 / 솔루션별 작업 현황 / 솔루션별 연동 현황 / GPU 사용 현황 / 로그 히스토리)은 중첩 라우트 + <router-view>로 배선했습니다. 설정 화면은 딥링크가 없어 탭 상태를 ref로 소유하지만, 모니터링은 대시보드의 [전체 로그 히스토리]처럼 특정 탭으로 직접 진입하는 경로가 있어 라우트가 정본이어야 합니다. 활성 탭은 라우트 name(monitoring-{tab})에서 단방향으로 파생되고, 탭 클릭은 router.push로 처리합니다. 5개 탭 모두 실제 구현이며, 화면 ID만 명시하던 플레이스홀더(MonitoringTabPlaceholder)는 폐기됐습니다.

현황 대시보드(MonitoringDashboardTab)는 GUI Contents 순서를 그대로 조립합니다 — 요약카드 6종, 작업현황 스택 막대, 연동현황 스택 막대, 연동률·GPU 2컬럼, 실시간 로그 표입니다. 위젯 5종은 self-contained라 각자 자기 쿼리 훅을 호출해 ChartFrame과 차트/표를 조립하고, [더보기]는 라우팅을 모른 채 emit만 올립니다. 컨테이너 자체가 라우트 컴포넌트여서 상위로 재emit 할 대상이 없으므로 여기서 router.push로 마감합니다. 요약카드는 예전에 오늘/전일 2쿼리로 전일 대비를 직접 차분했지만, API v1.0.7이 응답에 prevDayCount를 담아주면서 1쿼리로 줄었고(어댑터가 한 응답 안에서 delta를 계산), 두 번째 쿼리·전용 실패 처리·날짜 헬퍼가 함께 사라졌습니다.

솔루션별 작업현황(WorkStatusPage)·연동현황(IntegrationStatusPage) 두 탭은 더 이상 플레이스홀더가 아니라, GUI Contents 3개(조회조건 → 도넛 → 통계 테이블)를 그대로 조립하는 공용 셸 stats/StatsPage.vue를 뼈대로 갖습니다. 두 화면의 차이는 axis(work/sync)·상태 컬럼·CSV 파일명뿐이라 그 값만 props로 채워 넘기고, 조회조건(솔루션·기간 프리셋·달력)은 useStatsFilter 컴포저블 하나가 담당합니다. 연동 축은 도넛(4세그먼트, 연동완료 합산)과 테이블(5칸, 연동완료가 자동/수동으로 분리 — API v1.0.6에서 resultList.autoLinked/manualLinked로 위치가 확정됨)의 칸 수가 다르며, 서버가 값을 안 채우면 두 칸은 0이 아니라 -로 표시해 "자동 0건"이라는 거짓 표시를 피합니다. CSV 다운로드는 화면 표시와 별도로 CSV 전용 DTO를 재조회해 만듭니다.

GPU 사용현황(GpuUsagePage)은 GUI 섹션 5개(요약카드 → 서버그룹/조회조건 → 트렌드 3종 → 저장 이력 → 서버 리소스 현황)를 조립하는 독립 구현으로, 조회조건은 통계 탭과 같은 useStatsFilter를 축만 바꿔 재사용합니다. overview 쿼리 1건에서 서버그룹·요약카드·서버 옵션을 함께 얻고, 서버 목록이 응답 전이면 '전체'만 있는 폴백 옵션으로 버팁니다. ⚠️ 트렌드·저장이력 두 엔드포인트는 원래 날짜 형식이 달랐는데(트렌드 yyyy-MM-dd / 이력 yyyy.MM.dd, 스펙 v1.0.4 명시) BE가 전 엔드포인트를 ISO로 통일하면서 그 변환이 이제는 이력 엔드포인트를 400으로 만듭니다 — GPU는 아직 수집 인프라가 없어 live로 드러나지 않았을 뿐, MN-002/003의 startDt→startDate 회귀와 같은 종류의 문제입니다. 규격서는 아직 점(.) 형식으로 적혀 있으므로 규격만 보고 점 변환을 되살리면 안 됩니다.

데이터 계약은 모니터링 API 실경로를 그대로 씁니다(다른 메뉴처럼 추상 경로 가설이 아닙니다). 응답은 공통 엔벨로프 {code, message, data}인데 code가 숫자 200과 문자 "OK"로 혼재해 isMonitoringEnvelopeSuccess가 양쪽을 허용하고, 실패면 unwrapMonitoringEnvelope가 throw 해 위젯 상태가 error로 파생됩니다. 연동현황(#5)과 연동률(#6)은 같은 queryKey를 공유하고 select만 다르게 두어 네트워크 1회로 두 위젯을 채웁니다. 위젯 상태는 deriveWidgetState가 error > loading > empty > ok 우선순위로 접습니다. "값을 아직 모르는" 로딩 판정은 공용 함수 unresolved(isLoading, isError, hasData)로 일반화됐습니다 — 원인은 재시도 백오프 대기가 아니라, 탭이 비활성(hidden)일 때 query-core의 retryer가 재시도를 그대로 일시정지시키는 것이었습니다(fetchStatus:'paused' → isFetching=false·isError=false인데 데이터도 없는 구간). 이 구간에서 골격값이 실측값처럼 노출되던 것을 unresolved가 작업·연동현황 위젯까지 막습니다. 대시보드 #8은 파라미터 없이 호출해 영향이 없지만, 조회기간 파라미터명이 startDt/endDt에서 startDate/endDate로 통일됐고 구 이름은 400이 아니라 조용히 무시(전체 결과 반환)되므로 기간을 붙일 일이 생기면 새 이름을 써야 합니다. 또한 작업현황 엔드포인트는 targetDate가 유효 파라미터가 아니게 되었고(요청 축이 startDate/endDate/serviceType로 교체) 요약카드(state-day-analysis)만 targetDate가 정상 동작합니다.

차트는 ECharts 래퍼(ChartFrame + StackedBarChart)로 공통화했습니다. ECharts는 canvas 렌더러라 var(--x) 문자열을 직접 읽지 못하므로 resolveCssVar가 숨겨진 엘리먼트의 color에 변수를 걸어 브라우저가 완전히 리졸브한 계산값을 읽어 옵니다. 커스텀 프로퍼티를 getPropertyValue로 직접 읽으면 중첩 var() 참조가 안 풀려 값이 비거나 var(...) 문자열이 그대로 나오기 때문입니다. 툴팁 다크 테마(chartTheme)는 시각 속성만 export 하고 trigger·formatter는 각 래퍼가 유지하며, 마크업 로직은 chartTooltipFormatter로 분리했습니다.

로그 히스토리(MN-005)는 자체 완결된 페이지로 만들어 탭 셸이 완성된 뒤 셸 children으로 이전했습니다 — 최종 URL /monitoring/log-history와 라우트 name은 그대로라 대시보드 #8 배선과 기존 링크는 영향받지 않습니다. 목록은 공통 리스트 패턴을 따르되 작업 서비스 칩을 BE 원본 코드로 확장해 보냅니다. 화면의 칩은 병합축(예: 개인화 포스터 = SEGIMAGE)인데 로그 행의 serviceType은 원본 코드(SEGPOST·SEGBANNER)라, 병합축을 그대로 실으면 매칭이 0건이 됩니다. ⚠️ 실측으로 확정된 더 큰 제약은 /api/log가 serviceType 다중값을 지원하지 않는다는 것입니다 — CSV로 묶어도(TENTHUMB,POSTER) 반복 파라미터로 나눠도 전부 0건이라, 칩을 2개 이상 고르면 항상 결과가 없고 "개인화 포스터" 칩은 하나만 골라도 2코드로 확장돼 0건이 됩니다(BE가 다중값을 받기 전까지 FE만으로는 해소 불가). 정렬은 로그 API가 createDate,asc/desc만 받고 "실패 우선" 프리셋 자체가 없음이 실측으로 확정되어 최신순 폴백이 유지되지만, 화면 정렬 셀렉트가 여전히 "검수필요·실패 우선" 문구를 보여주면서 실제로는 항상 최신순으로 동작하는 라벨-동작 불일치가 남아 있습니다. 「API명」 필터는 예전엔 mock에서 뽑은 5종을 하드코딩해 실 BE 값과 교집합이 0(무엇을 골라도 0건)이었으나, 규격 v1.0.9가 신설한 GET /api/code/log-endpoints(실측 69종)로 옵션을 조달하도록 바뀌었습니다(useApiEndpointOptions) — 라벨도 BE 값을 그대로 쓰고 FE가 표를 만들지 않습니다.

설계 포인트 — feature 간 직접 import 금지
로그 히스토리의 wire 파라미터는 대시보드 #8의 타입과 동일한 필드셋인데도 재사용하지 않고 같은 모양으로 다시 선언했습니다. ESLint no-restricted-imports가 @/features/*/* 그룹을 전면 금지해 feature 간 직접 import가 불가능하고(공통화하려면 shared/·api/·domain/으로 승격해야 함), 그 승격이 다른 담당자의 산출물 변경을 요구해 이번 범위를 벗어났기 때문입니다. 의도와 사유는 코드 주석과 구현 보고서에 남겨 두었습니다.

src/features/monitoring/dashboard/queries.ts — queryKey 공유와 위젯 상태 파생
export function deriveWidgetState(opts: {
  isLoading: boolean
  isError: boolean
  isEmpty: boolean
}): WidgetState {
  if (opts.isError) return 'error'
  if (opts.isLoading) return 'loading'
  if (opts.isEmpty) return 'empty'
  return 'ok'
}

/** #6 연동률 — sync-state 원본을 연동률로 파생(select). #5 와 queryKey 공유(네트워크 1회). */
export function useIntegrationRateQuery(targetDate?: MaybeRefOrGetter<string | undefined>) {
  const query = useQuery({
    queryKey: computed(() => monitoringKeys.syncState(toValue(targetDate))),
    queryFn: () => fetchSyncState(toValue(targetDate)),
    select: toIntegrationRate,
  })
  const data = computed<IntegrationRateView>(() => query.data.value ?? EMPTY_RATE)
  const state = computed<WidgetState>(() =>
    deriveWidgetState({
      isLoading: query.isLoading.value,
      isError: query.isError.value,
      isEmpty: data.value.bySolution.length === 0,
    }),
  )
  return { data, state }
}

/**
 * "값을 아직 모르는 구간"을 loading 으로 본다 — 위젯들의 isLoading 입력용.
 * ⚠️ query.isLoading(=isPending && isFetching) 만으로는 재시도 대기 구간이 빈다.
 *    retryDelay 사이의 대기는 문서가 비활성(hidden)이면 query-core retryer 의 canContinue()가
 *    그대로 일시정지시킨다 → fetchStatus 가 'paused' 라 isFetching=false, isError 도 아직 false.
 *    그 구간에서 data 는 undefined 인데 소비처가 골격으로 채워 isEmpty 가 true 로 잘못 떨어진다
 *    (2026-08-18 실측: 비활성 탭에서 1.3초 후 empty 로 전환되고 탭 복귀까지 유지).
 * 값을 못 받았고 에러도 아니면 아직 진행 중이다 — '없음'이 아니라 로딩이다.
 */
export function unresolved(isLoading: boolean, isError: boolean, hasData: boolean): boolean {
  return isLoading || (!hasData && !isError)
}

export function useWorkStatusQuery(targetDate?: MaybeRefOrGetter<string | undefined>) {

  return { data, state }
}

src/api/monitoringTypes.ts — code 혼재를 흡수하는 공통 엔벨로프
/** 공통 엔벨로프 — code 는 숫자(200)|문자("OK") 혼재 */
export interface MonitoringEnvelope<T> {
  code: number | string
  message: string
  data: T
}

/** 엔벨로프 code 성공 판정 — 200(숫자) 또는 "OK"(문자) 양쪽 허용 */
export function isMonitoringEnvelopeSuccess(code: number | string): boolean {
  return code === 200 || code === 'OK'
}

/** 엔벨로프에서 data 추출 — 실패 code 면 throw(호출측이 catch → WidgetState:'error' 파생) */
export function unwrapMonitoringEnvelope<T>(envelope: MonitoringEnvelope<T>): T {
  if (!isMonitoringEnvelopeSuccess(envelope.code)) {
    throw Object.assign(new Error(`monitoring API error: ${envelope.message}`), {
      code: envelope.code,
    })
  }
  return envelope.data
}
src/shared/components/composite/chart/resolveCssVar.ts — canvas 차트를 위한 CSS 변수 리졸브
// echarts 는 canvas 렌더러라 `var(--x)` 문자열을 직접 못 읽는다.
// ⚠️ getComputedStyle(el).getPropertyValue('--status-dot-waiting') 로 커스텀 프로퍼티 자체를 읽으면
//    중첩 var(--c-...) 참조가 안 풀려 값이 비거나 'var(...)' 문자열이 그대로 나올 수 있다.
//    반드시 실제 CSS 프로퍼티(color)에 걸어 브라우저가 완전히 리졸브한 계산값을 읽는다.
export function resolveCssVar(varName: string): string {
  const el = document.createElement('span')
  el.style.color = `var(${varName})`
  el.style.display = 'none'
  document.body.appendChild(el)
  const resolved = getComputedStyle(el).color
  el.remove()
  return resolved
}

// 🔴 왜 만들었나. 종전 constants.ts KNOWN_ENDPOINTS 5종은 mock fixture 에서 뽑은 값이라 실 BE
//    값과 교집합이 0 이었다 — live 에서는 무엇을 골라도 조용한 0건(400 이 아니라 신호가 없었다).
//    규격 v1.0.9 가 신설한 모니터링#12 GET /api/code/log-endpoints(실측 200 · 69종)로 대체한다.
// ⚠️ 라벨을 FE 가 만들지 않는다 — 규격 예시 문구가 실 BE 문구와 이미 어긋나 있었다.
export function toApiEndpointOptions(items: LogEndpointItemDto[]): VSelectOption<string>[] {
  const all = items.find((i) => i.endpoint === 'all') // BE 가 '전체'로 쓰는 코드(FE sentinel 과 별개)
  return [
    { value: API_ENDPOINT_ALL, label: all?.label ?? '전체' },
    ...items.filter((i) => i.endpoint !== 'all').map((i) => ({ value: i.endpoint, label: i.label })),
  ]
}
