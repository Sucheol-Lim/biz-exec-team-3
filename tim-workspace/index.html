개요

tim-workspace는 TIM(Telecom Italia)의 라이브 OTT 서비스 "TIMVISION" 클라이언트 앱 개발을 위한 문서 + submodule 포인터 통합 저장소입니다. 저장소 자체는 빌드 대상이 아니며, 00.overview(제품 정의)부터 90.release(릴리즈)까지 십의 자리 라이프사이클 순서로 번호가 매겨진 폴더 아래에 회의록·요구사항·설계 산출물과 실제 개발 라이브러리(50.dev-library)·클라이언트 앱(60.dev-app) submodule을 담습니다. backend는 이 프로젝트 범위 밖(ZTE 소관)입니다.

플랫폼은 일의 자리 번호로 매겨진 4개 레인으로 나뉩니다 — 1(Android): 51.player-kt+56.core-kt+61.app-tv-android, 2(Apple): 52.player-swift+57.core-swift+62.app-tv-tvos, 3(Flutter): 53.player-flutter+58.core-dart+63.app-mobile-flutter, 4(Web): 54.player-js+59.core-js+64.app-web. 착수 순서는 1차 Android → 2차 Mobile(Android 백엔드 우선) → 3·4차 Web → 5차 tvOS이며, 현재 원격 repo가 등록된 것은 1차 레인(Android) 3개 submodule뿐입니다(51.player-kt·56.core-kt·61.app-tv-android). 나머지 레인은 원격 repo 생성 대기 상태입니다.

1차 레인의 실체는 기존 Türk Telekom Tivibu Android 4K STB 코드베이스의 포크입니다. app-tv-android의 README.md 제목이 여전히 "Tivibu Android 4K"이고 applicationId도 tivibu.android.stb이며, app/src에는 stvOtt·tivibuEv·zteAosp 3개 플레이버가, dependency/platform에는 tt4k·smarttv 모듈이 그대로 남아 있습니다. 백엔드 연동 레이어(core-kt/si)도 기존 TT4K 구현(impl-tt4k)을 재사용 기반으로 두고, TIM 전용 백엔드가 아직 없는 구간은 목업 구현(impl-mock)으로 우회해 개발이 진행되고 있습니다.

아직 RFP가 불확실한 초기 단계

사내 Confluence(ORGAPPDEV, "99.01. TIM Live OTT 클라이언트·Player 기술 검토", 2026-08-30)에 따르면 현재 설계 장표는 불명확한 RFP를 구조화한 가설 기반 아키텍처 초안이며, 지원 단말 범위·DTT 수신제한(CAS) 유무·Web 단일 코드베이스 가능 여부·SDUI 적용 수준 등 다수 항목이 고객·벤더 협의(2026년 9월 현지 협의 예정) 전까지 미확정입니다. 아키텍처 원칙은 "하나의 Player 엔진을 모든 플랫폼에 이식하지 않고, Common Player Contract(Command·State·Event·Error·Capability)를 여러 플랫폼별 Adapter가 준수"하는 방식이며, 플랫폼별 지원 범위는 Standard / Legacy·Conditional / Unsupported / Out-of-Scope 4단계 Support Tier로 판정합니다.

주요 기능

홈 · 내비게이션 엔진
nav/engine의 Destination·DestinationStacks·KeyRouter가 화면 스택과 리모컨 키 입력을 관리하고, 구 screenlayer를 대체한 nav/app과 GNB·행 목록으로 새로 교체된 ui/home(HomeScreen) 위에서 홈 화면을 구성합니다.
라이브 TV 시청
LiveTvScreen·LiveTvViewModel이 미니가이드(MiniGuideView), PIP(PipView), 모자이크 채널(MosaicView/MosaicUseCase), 채널 OSD·핑거프린트 워터마크(FingerPrintView)를 통합합니다.
재생 오케스트레이션
PlayOrchestrator가 core-kt의 PlayStarter/PlayStateHolder/CurrentPlayControl 3역할을 구현하고, 새로 분리된 PlayHub가 TsTv·PlTv·NPVR·단편/시리즈 VOD·트레일러·프리뷰 등 7종 PlayHandler로 재생을 분기해 ChannelPlayBar/VodPlayBar/StartOverPlayBar 컨트롤 UI를 구성합니다.
Player 코어 (Common Player Contract)
51.player-kt가 Media3/ExoPlayer 기반 재생 엔진을 PlayerAdapter 계약 뒤로 감추고 IMA 광고(ImaAdSupport)를 지원합니다. 앱 쪽 core/impl-mock/impl-tt4k 어댑터는 app-tv-android에서 core-kt로 이전됐습니다.
서비스 인터페이스(SI) 추상화
core-kt/si가 채널·EPG·예약 백엔드 접근을 인터페이스로 추상화합니다. 같은 저장소에 v8.26 RFQ 스펙용 data2/domain2 계층이 18개 도메인 그룹으로 새로 구축됐습니다.
부팅 · 페일세이프 복구
BootScreen이 nav 엔진의 타입 있는 Args(countOn, message)로 이관되어 페일세이프 에러 코드·재시도 카운트를 보여줍니다. 다운로드 진행률 표시 모드는 삭제됐습니다.
설정 · 사용자 환경
CAS 정보(CasInfoView), 시청등급 제어(ParentalControlView), 녹화/예약 내역(MyRecordsView/MyRemindersView), 대여·구매 이력(RentalPurchaseHistoryView) 등 45개 설정 화면·뷰모델로 구성됩니다(공장 초기화/재부팅 메뉴는 삭제).
팝업 · 오버레이
레거시 ATVPopup/BaseAnimationPopup이 삭제되고, 모든 팝업이 nav 엔진의 AppFragment+DestinationSpec으로 통일됐습니다. 프로필 로그인(ui/home/subview/profile/popup), 페일세이프 복구(FailSafeRecoveryPopup), 전역 에러(GlobalErrorPopup) 등 26개 팝업이 있습니다.
빌드 플레이버 · 기존 자산 재사용
tivibuEv가 jade로 개명(applicationId는 유지)됐고 zteAosp는 비활성화됐습니다. dependency/platform의 tt4k 모듈도 jade로 개명되어, 기존 Türk Telekom Tivibu Android 4K 코드베이스 유래를 이름에서부터 지우는 중입니다.

목표 스택과 현재 소스의 차이

60.dev-app/CLAUDE.md는 61.app-tv-android의 스택을 "Kotlin · Compose for TV · Media3"로 명시하지만, 실제 소스(app/, core-kt/, nav/)에는 @Composable 사용이나 androidx.compose 의존성이 전혀 없습니다 — 현재는 Fragment/ViewBinding 기반이며, 새 홈 UI의 행 렌더링도 Compose가 아니라 자체 rvx(RecyclerView 확장) 어댑터 위젯 체계로 구현됐습니다. Compose for TV는 아직 목표(가정)이지 현재 구현 상태(확정)가 아닙니다. Confluence 문서(01. Multi-Platform Player Feasibility & Delivery Baseline)에 따르면 최종 지원 플랫폼·DRM·코덱·화질도 아직 Standard/Legacy Support Tier 판정 전이며, 위 스택은 1차 Android 레인의 현재 소스 기준입니다. Apple(AVPlayer/FairPlay)·Web(JS Player+EME) 레인은 아직 코드가 없습니다.

핵심 동작 흐름

앱 기동 → 홈 진입 (정상 경로)

  1. 앱 기동com.tim.play.TivibuApplication이 AppLifecycleCallback·LifecycleObserveApplication으로 앱 생명주기를 관찰하며 초기화를 시작합니다.
  2. 홈 진입nav/engine의 Navigator·KeyRouter가 Destination 스택을 홈으로 전이시켜, GNB·행 목록 기반으로 새로 교체된 HomeScreen을 표시합니다(구 menu/MenuView는 삭제됨, f01 참고).

페일세이프 복구 경로 (비정상 부팅)

  1. 복구 모드 진입단말 소프트웨어 손상 등으로 Navigator가 타입 있는 BootScreen.Args(countOn, message)와 함께 BootScreen을 활성화합니다.
  2. 상태 표시BootViewModel이 StorageRepository의 에러코드·재시도 카운트 스트림을 구독해 화면을 실시간 갱신합니다. 다운로드 진행률 표시 모드는 레거시 정리 과정에서 제거됐습니다(f06 참고).

채널 시청 · 재생 요청 분기

  1. 채널 선택LiveTvScreen에서 채널을 선택하면 ChannelPlayBarViewModel이 재생을 요청합니다.
  2. UseCase 조회PlayOrchestrator(core-kt의 PlayStarter 구현체)가 15개 Play*UseCase 중 콘텐츠 성격에 맞는 것(예: PlayTsTvUseCase)으로 URL·권한을 먼저 조회합니다.
  3. 핸들러 분기조회 결과를 새로 분리된 PlayHub에 넘기면, PlayHub가 VodType(TsTv/PlTv/NPVR·PPV/단편·시리즈 VOD/트레일러/프리뷰)에 따라 7종 BasePlayHandler 중 하나를 선택합니다(f03).
  4. SI → Player 위임핸들러가 core-kt/si(impl-mock 또는 impl-tt4k)로 재생 URL·권한 정보를 확정한 뒤, player-kt의 PlayerAdapter 계약을 통해 실제 재생 엔진(ExoPlayer)에 전달합니다.
  5. 컨트롤 UI 표시ChannelPlayBar/VodPlayBar/StartOverPlayBar가 재생 상태(PlayerState)를 구독해 컨트롤 UI를 갱신합니다.

플레이버별 분기 (기존 자산 재사용)

  1. 플레이버 선택Gradle 빌드 시 jade(기본, 구 tivibuEv)·stvOtt 중 하나를 선택해 AndroidManifest.xml과 dependency/platform/{jade,smarttv}(구 tt4k) 조합이 정해집니다. zteAosp는 enum 등록이 주석 처리돼 현재 선택할 수 없습니다(f09).
  2. 백엔드 재사용 vs 목업TT4K 연동이 살아있는 경로는 si/impl-tt4k·player/impl-tt4k가, TIM 전용 백엔드가 아직 없는 경로는 si/impl-mock·player/impl-mock이 담당합니다. 두 계층 모두 이제 core-kt 저장소 안에 있습니다(f04·f05).

빌드 · 실행

전체를 받으려면 submodule을 recursive로 함께 받아야 합니다 — core-kt·player-kt는 이제 50.dev-library 아래 한 곳에만 존재하고, app-tv-android는 settings.gradle.kts의 includeBuild(file("../../50.dev-library/..."))로 그 형제 경로를 상대 참조하므로 워크스페이스를 통째로 clone해 세 submodule이 정해진 상대 위치에 함께 있어야 빌드가 됩니다. 선행 조건은 Bitbucket SSH 키 등록(ssh -T git@bitbucket.org)입니다.

# 전체 clone (문서 + 1차 레인 submodule 전부)
git clone --recurse-submodules git@bitbucket.org:altimedia/tim-workspace.git

# 이미 clone했다면
git submodule update --init --recursive

# tv-android 파트만 필요하면 (문서만 볼 게 아니라면)
git submodule update --init --recursive \
  50.dev-library/51.player-kt \
  50.dev-library/56.core-kt \
  60.dev-app/61.app-tv-android

app-tv-android 자체 빌드는 Gradle Wrapper를 사용하며, player-kt는 include가 아니라 includeBuild(Composite Build)로 소비되므로 일반 clone만으로는 소스가 딸려오지 않습니다 — 위 recursive 절차가 반드시 필요합니다.

  • player-kt·core-kt 안에서 만든 커밋은 각각 tim-player-kt·tim-core-kt repo에 별도로 push해야 하며, 워크스페이스 루트는 그 커밋의 SHA를 gitlink로만 기록합니다. push 순서가 중요합니다 — 라이브러리 쪽을 먼저 push한 뒤 상위를 push해야 다른 사람의 git submodule update가 실패하지 않습니다.
  • app-tv-android 최신 커밋(cc4a6cb)에 새로 추가된 harness verification adapter([build] add harness verification adapter)는 워크스페이스 harness/의 검증 절차를 앱 빌드에서 직접 호출하기 위한 어댑터입니다. 워크스페이스 자체의 AI 개발 워크플로우는 harness/가 Claude Code plugin(tim-harness)으로 제공하며, 번호 체계 밖의 개발 도구입니다.
