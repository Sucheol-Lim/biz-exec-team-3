권한 기반 사이트 전환 제어

SiteGuard·checkPermission이 사용자 권한 레벨(hasRole)에 따라 사이트 간 전환을 판정합니다. 부적합 접근 시 WebSocket을 해제하고 세션을 정리한 뒤 로그인으로 이동합니다.

기능 개요

사용자 권한은 USER_ROLES 5단계입니다. 인덱스 0(서비스 고객)부터 4(플랫폼 관리자)까지이며, hasRole(targetLevel)이 세션 사용자(user.userRoleId)의 권한 인덱스가 목표 레벨 이상인지 판정합니다. 즉 hasRole(4)는 플랫폼 관리자, hasRole(3)은 서비스 관리자 이상을 의미합니다.

SiteGuard는 라우팅 최상위(/:site)에서 먼저 URL의 site가 ALLOWED_SITE_PATHS에 있는지 확인합니다. 다음으로 현재 세션 사이트(currentSite)와 이동 대상 사이트(target)를 checkPermission에 넘겨 전환 가능 여부를 판정합니다. 같은 사이트로의 이동이거나 대상이 없으면 항상 허용합니다.

checkPermission 규칙은 다음과 같습니다. 플랫폼 관리자(hasRole(4))는 모든 전환을 허용합니다. 서비스 관리자(hasRole(3))는 Air Map ↔ 과천, SafeMate 4종 상호 간 전환만 허용하고 그 외는 거부합니다. 나머지 권한은 다른 사이트로의 전환을 허용하지 않습니다. 판정이 부적합(!isValidAccess)이면 useEffect에서 WebSocket을 disconnect()하고 sessionStorage.clear()한 뒤 /:urlSite/login으로 리다이렉트합니다.

사이트 진입 경로(SITE_LIST[].path)는 운영 반영 과정에서 air→airbiz, dx→factorydx, gwacheon→airmon으로 변경되었습니다. SITE_CODES가 SITE_LIST.find((s) => s.path === ...)로 사이트 코드를 역참조하는 구조라 경로 상수 변경이 곧 코드 매핑에 직결됩니다. 사이트 코드(001ENV301 등)와 realcode는 그대로이므로 checkPermission 판정 규칙 자체는 변하지 않습니다.

사이트 전환 메뉴 정의(SITE_MENU)에서 AI산업안전DX는 AIENVDX_SERVICE_TYPE_LIST 기반 5개 서비스 유형(산업대기질·자원순환·산업환경·탄소중립·제조공정)에 더해, 유형 필터를 해제하는 전체 항목(AIDX_ALL_SERVICE_TYPE = 'ALL')이 앞에 추가되어 6개 하위 메뉴가 되었습니다. 여섯 항목 모두 같은 사이트 코드(001ENV302)를 쓰므로 checkPermission에서는 동일 사이트 이동으로 항상 허용되고, 실제 구분은 각 메뉴의 serviceType 값으로 이뤄집니다. 서비스 유형 단위 접근 제한도 config에 있어, 위젯 설정 화면은 isWidgetSettingServiceType()(현재 제조공정 ENVSMAT30203만 허용) 판정을 따릅니다.

사이트 전환 이후의 화면 노출은 메뉴 단계에서 한 번 더 권한으로 걸러집니다. getMenuList(siteCode, serviceType)는 AI산업안전DX에서 서비스 고객(!hasRole(1))일 때 종합 현황·서비스대상 관리·디바이스 관리 메뉴를 만들지 않고, 구역 관리는 제조공정(AIDX_MANUFACTURING_PROC)에서만 예외적으로 노출합니다. 한전 AMI는 KT 요청으로 주석 처리돼 있던 현황(overview)·배전선로 작업현황(amiLineTaskStatus) 메뉴가 다시 노출되도록 복구되었습니다.

메뉴 조립 함수는 캐시 유무로 두 갈래가 되었습니다. 실제 조립은 순수 함수 buildMenuList(siteCode, serviceType)가 맡고, getMenuList는 그 결과를 cachedMenuList에 담아 돌려줍니다. 덕분에 현재 화면의 캐시를 건드리지 않고도 임의의 사이트·서비스 유형에 대한 메뉴를 다시 계산할 수 있습니다. 여기에 하위 메뉴 id 집합을 만드는 getAvailableMenuIds(menuList)와 목록에서 경로를 찾는 getMenuPathFromList(menuList, menuId)가 더해져, 권한 판정 결과를 메뉴 id 단위로 재사용합니다.

이 구조는 통합 검색(SmartSearch)의 결과 이동 제어에 쓰입니다. 검색 결과를 클릭하면 isSmartSearchResultAvailable(components/search/smartSearchFilter.ts)이 결과 유형별 대상 메뉴 id를 먼저 구합니다. 디바이스는 Air Map이면 stationStatus, 그 외에는 devices, 서비스대상은 serviceTargets, 구역은 zones, 메뉴 결과는 menuType이 대상입니다. 이 id가 현재 권한 메뉴 집합에 없으면 이동 자체를 막습니다. 메뉴 유형이 아닌 결과는 unitServiceCode가 세션 사이트의 realcode와 같을 때만 통과시켜 다른 단위서비스의 데이터로 넘어가지 않게 하고, 지도(map) 결과는 판정 대상에서 제외합니다.

가드 적용 범위의 예외도 있습니다. SMS 수신동의 페이지(/:site/sms-consent)는 로그인과 무관하게 접근해야 하는 공개 페이지라, SiteGuard·ProtectedRoute 트리 밖의 독립 형제 라우트로 배치되어 전환 판정을 타지 않습니다. 반대로 가드를 통과한 뒤에는 Home·Overview 라우트가 AutoRefreshRoute(scope home/overview)로 한 겹 더 감싸집니다. 이 컴포넌트는 useParams()의 site를 key에 넣어, 사이트가 바뀌면 자동 갱신 바운더리가 통째로 재마운트되고 새 타이머가 현재 시각부터 다시 시작하도록 합니다.

2026-09-15에는 사이트 전환과 별개로, 같은 사이트 안에서도 메뉴 단위 서비스 가입 여부를 확인하는 계층이 추가되었습니다. Air Map의 전문가 보고서(expertAnalysis)·공기질 알림 SMS 설정(smsAlarm) 두 메뉴는 isMenuServicePermissionTarget(site.code, menuType)이 대상인지 먼저 가리고, 대상이면 checkMenuServicePermission이 commonApi.getMenus(serviceType) 응답의 menuTemplate으로 실제 menuId를 찾은 뒤(KT DEV 응답의 menuType은 메뉴 종류라 식별에 쓸 수 없어, 계층형 코드인 menuId 대신 menuTemplate로 매칭합니다) commonApi.checkMenuExtService({ serviceTargetId, menuId })로 가입 여부(boolean)를 확인합니다. 이동 경로는 두 갈래입니다. 사이드바 메뉴(MenuList)·통합 검색(SmartSearch)·즐겨찾기(FavoritList)처럼 클릭으로 진입하는 경로는 requestMenuServiceEntry가 이동 전에 확인해, 권한이 있을 때만 실제 navigate를 실행하고 없으면 안내 팝업만 띄운 채 현재 화면에 머무릅니다. 주소를 직접 입력하거나 새로고침·뒤로가기로 들어오는 클릭 없는 진입은 라우트에 씌운 MenuServicePermissionGuard가 같은 확인을 한 번 더 수행하고, 확인 전까지는 화면을 렌더하지 않다가 거부되면 Home으로 replace 이동합니다. 검색 팝업·즐겨찾기 목록은 클릭 즉시 닫혀 컴포넌트가 사라지므로, 확인 결과 처리와 안내 팝업 상태는 컴포넌트가 아니라 모듈 전역 상태로 관리하고 MainLayout에 한 번만 마운트되는 MenuServicePermissionHost가 그 상태를 구독해 팝업을 그리고 상주하는 navigate로 실제 이동을 수행합니다. 클릭 경로에서 확인을 통과한 이동은 grantEntryPass로 10초짜리 1회용 통과 표시를 남겨, 곧바로 이어지는 라우트 가드의 재확인을 consumeEntryPass가 건너뛰게 합니다. 두 API 모두 5초 타임아웃을 두고, 응답 형식이 기대(boolean)와 다르거나 대상 메뉴를 찾지 못하는 등 API 오류가 아닌 판정 실패는 openError({ status: '999' })로 공통 오류 팝업을 직접 띄웁니다(HTTP 오류·타임아웃은 인터셉터가 이미 띄웁니다).

SiteGuard의 훅 호출 순서 결함도 함께 정리되었습니다. 이전에는 site가 ALLOWED_SITE_PATHS에 없으면 useLocation·이후 로직에 도달하기 전에 return <Error />로 먼저 빠졌는데, 렌더마다 이 분기 결과가 뒤집힐 수 있어 호출되는 훅의 개수가 렌더 간에 달라지는 React 규칙 위반이었습니다. 지금은 useLocation을 조기 반환보다 앞으로 올리고, 판정 로직은 isKnownSite(경로 유효성)와 isValidAccess(target이 있을 때만 checkPermission 호출)로 나눠 target이 없는 상태에서 checkPermission이 prevSite.code 접근으로 크래시하지 않게 가드합니다. 세션 정리 useEffect도 "허용된 site 경로일 때만" 정리하도록 isKnownSite 조건을 추가해, Error 화면으로 빠지는 경로에서는 기존처럼 세션을 건드리지 않습니다. ProtectedRoute 역시 세션 site가 없을 때 site?.path를 그대로 문자열에 넣어 /undefined/login으로 이동시키던 결함을 고쳐, 세션이 없으면 URL 첫 세그먼트를 대신 씁니다.

설계 포인트
세션 정리와 WebSocket 해제를 부적합 접근 시 즉시 수행해, 권한 없는 다른 사이트의 실시간 채널·토큰이 남지 않도록 합니다. 보호 진입 자체는 별도로 ProtectedRoute가 세션 site.code 유무로 한 번 더 가립니다.

흐름. 전환 시 SiteGuard가 권한을 판정하고, 부적합하면 WebSocket·세션을 정리한 뒤 로그인으로 보냅니다. 통과하면 Home·Overview는 AutoRefreshRoute가 사이트 단위로 재마운트하고, 메뉴는 getMenuList가 권한·서비스 유형으로 한 번 더 걸러 렌더합니다. SMS 수신동의 페이지는 가드 밖 독립 라우트라 이 판정을 거치지 않습니다. 통합 검색은 같은 메뉴 조립 결과를 다시 계산해 접근 불가한 결과로의 이동을 막습니다.

관계. SiteGuard가 checkPermission·hasRole로 전환을 판정하고, 부적합 시 WebSocket을 끊으며, 적합하면 ProtectedRoute 보호 진입으로 넘깁니다. 그 안에서 Home·Overview는 AutoRefreshRoute가 사이트 단위로 감싸고, 메뉴는 getMenuList가 권한으로 다시 걸러냅니다. SmartSearch는 순수 조립 함수 buildMenuList로 같은 권한 메뉴를 다시 만들어 검색 결과 이동 가능 여부를 판정합니다.

핵심 코드

src/routes/route.tsx — 권한 기반 전환 판정
const checkPermission = (prevSite, nextSite) => {
  if (!nextSite || prevSite.code === nextSite.code) return true;
  if (hasRole(4)) return true;                       // 플랫폼 관리자: 모두 허용
  if (hasRole(3)) {                                  // 서비스 관리자: 제한 허용
    if (prevSite.code === SITE_CODES.AIRMAP && nextSite.code === SITE_CODES.GWACHEON) return true;
    if (prevSite.code === SITE_CODES.GWACHEON && nextSite.code === SITE_CODES.AIRMAP) return true;
    // SafeMate 4종 상호 전환 허용 ...
  }
  return false;
};
src/routes/route.tsx — 부적합 시 세션·WebSocket 정리
const isValidAccess = checkPermission(target, currentSite);
useEffect(() => {
  if (!isValidAccess) {
    disconnect();              // STOMP 연결 해제
    sessionStorage.clear();    // 토큰/사이트/사용자 세션 정리
  }
}, [isValidAccess]);
if (!isValidAccess) return <Navigate to={`/${urlSite}/login`} replace />;
src/routes/route.tsx · src/routes/ProtectedRoute.tsx — 훅 호출 순서 고정 · undefined 경로 방지
const SiteGuard = ({ children }: { children: React.ReactNode }) => {
  const { site } = useParams();
  const { disconnect } = useWebSocket();
  // 조기 return 보다 항상 먼저 호출되도록 위치를 고정한다 (렌더 간 훅 개수 불일치 방지)
  const location = useLocation();

  const isKnownSite = Boolean(site && ALLOWED_SITE_PATHS.includes(site));
  const target = SITE_LIST.find((obj) => obj.path === location.pathname.split('/')[1]);
  // target 이 없는 상태로 checkPermission 을 부르면 prevSite.code 접근에서 크래시하므로
  // 실제 크래시 조건(target 존재 여부)을 직접 가드한다
  const isValidAccess = Boolean(target) && checkPermission(target, currentSite);

  useEffect(() => {
    // 허용된 site 경로일 때만 정리한다 — Error 로 빠지는 경로는 세션을 건드리지 않는다
    if (isKnownSite && !isValidAccess) {
      disconnect();
      sessionStorage.clear();
    }
  }, [disconnect, isKnownSite, isValidAccess]);

  if (!isKnownSite) return <Error />;
  if (!isValidAccess) return <Navigate to={`/${urlSite}/login`} replace />;
  return children;
};

// ProtectedRoute: site 가 없을 때 site?.path 를 그대로 쓰면 '/undefined/login' 이 된다
export default function ProtectedRoute() {
  const site = getSessionStorage('site');
  const location = useLocation();
  if (!site?.code) {
    const firstSegment = location.pathname.split('/')[1];
    return <Navigate to={`/${site?.path ?? firstSegment}/login`} replace />;
  }
  return <Outlet />;
}

// KT DEV 응답의 menuType은 메뉴 종류(MENU/PAGE)라 식별에 못 쓴다 — menuTemplate으로 menuId를 찾는다
const getMenuIdMap = (realcode, serviceType) =>
  commonApi.getMenus(serviceType, { timeout: 5000 }).then((data) => {
    const map = {};
    for (const row of data?.rows ?? []) if (row?.menuTemplate && row?.menuId) map[row.menuTemplate] = row.menuId;
    return map;
  });

export const checkMenuServicePermission = async (menuType, serviceTargetId) => {
  const menuId = (await getMenuIdMap(site.realcode, user?.serviceType))[BFF_MENU_TEMPLATE_BY_TARGET[menuType]];
  if (!menuId) { reportLocalFailure(); return 'failed'; }
  const result = await commonApi.checkMenuExtService({ serviceTargetId, menuId }, { timeout: 5000 });
  if (typeof result !== 'boolean') { reportLocalFailure(); return 'failed'; }
  return result ? 'allowed' : 'denied';
};

// 클릭 경로 — 확인 후 이동. 확인 중 다른 클릭이 오면 마지막 요청만 반영한다
export const requestMenuServiceEntry = async ({ menuType, serviceTargetId, onAllowed }) => {
  const requestId = ++latestClickRequestId;
  const result = await checkMenuServicePermission(menuType, serviceTargetId);
  if (requestId !== latestClickRequestId) return;
  if (result === 'allowed' && serviceTargetId) { grantEntryPass(menuType, serviceTargetId); onAllowed(); }
  else if (result === 'denied') showNoServicePermissionAlarm();
};

// 주소 직접 입력·새로고침·뒤로가기 진입 가드 — 확인 전에는 화면을 렌더하지 않는다
export const MenuServicePermissionGuard = ({ menuType, children }) => {
  const isTarget = isMenuServicePermissionTarget(site?.code, menuType);
  const [allowed, setAllowed] = useState(false);
  useEffect(() => {
    if (!isTarget || !serviceTargetId) return;
    if (consumeEntryPass(menuType, serviceTargetId)) { setAllowed(true); return; }   // 클릭 경로 재확인 생략
    checkMenuServicePermission(menuType, serviceTargetId).then((result) => {
      if (result === 'allowed') setAllowed(true);
      else if (result === 'denied') showNoServicePermissionAlarm(() => navigate(`/${site?.path}/home`, { replace: true }));
      else navigate(`/${site?.path}/home`, { replace: true });   // failed: 오류 팝업은 이미 표시됨
    });
  }, [isTarget, menuType, serviceTargetId, navigate]);
  if (!isTarget) return <>{children}</>;
  return allowed ? <>{children}</> : null;
};
